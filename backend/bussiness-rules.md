# 业务规则与计划生成规范

- 文档版本：V1.0
- 对应需求文档：《天气查询与智能出行规划助手》软件需求规格说明书 V1.0
- 对应接口契约：`openapi/travel-assistant.yaml`
- 适用模块：天气规则判断、活动推荐、建议生成、单日出行计划组装
- 实现技术：Java + Spring Boot
- 规则实现方式：Java 条件判断，不引入额外规则引擎

## 1. 文档目的

本文档用于明确业务规则与计划生成模块的输入、判断条件、执行优先级、输出要求和异常数据处理方式，作为 Java 业务逻辑实现与单元测试的共同依据。

本模块不负责调用 Open-Meteo API、解析原始天气 JSON、进行城市地理编码或渲染 Thymeleaf 页面。天气数据由天气查询模块提供，计划结果由页面模块展示。

## 2. 模块输入与输出

### 2.1 输入

#### TravelRequest

依据接口契约，出行请求包含以下字段：

| 字段                 | 类型                       | 说明                                         |
| -------------------- | -------------------------- | -------------------------------------------- |
| `city`               | String                     | 目的地城市名称                               |
| `date`               | LocalDate 对应的日期字符串 | 出行日期，格式为 `YYYY-MM-DD`                |
| `activityPreference` | String 或约定的枚举类型    | 活动偏好，只允许 `OUTDOOR`、`INDOOR`、`FOOD` |

字段名称、枚举值和含义必须与接口契约一致，不得自行添加或修改公共请求字段。

#### WeatherData

| 字段                       | 类型     | 说明                                        |
| -------------------------- | -------- | ------------------------------------------- |
| `date`                     | 日期     | 天气预报对应的日期                          |
| `weatherCode`              | Integer  | Open-Meteo 使用的 WMO 天气代码              |
| `maxTemp`                  | 数值     | 最高温度，单位 °C                           |
| `minTemp`                  | 数值     | 最低温度，单位 °C                           |
| `precipitationProbability` | 可空整数 | 降水概率，单位 %                            |
| `windSpeed`                | 可空数值 | 风速，单位 km/h，须与天气模块的单位约定一致 |

**数据前提：** 本模块使用标准化后的 `WeatherData`，不直接解析外部 API 响应。可空字段必须按缺失数据处理规则进行判断，不得将 `null` 直接替换为 0。

如果实际 DTO 还包含降水量等字段，应先确认其已纳入公共契约，再决定是否使用；不得假定未定义字段一定存在。

### 2.2 输出：TravelPlan

计划生成成功时，返回契约约定的 `TravelPlan`，包含：

| 字段                | 生成要求                                 |
| ------------------- | ---------------------------------------- |
| `city`              | 与请求中的目的地一致                     |
| `date`              | 与请求日期及实际使用的天气日期一致       |
| `weatherSummary`    | 天气概况；不能包含无数据依据的确定性结论 |
| `morningActivity`   | 上午活动建议                             |
| `afternoonActivity` | 下午活动建议                             |
| `eveningActivity`   | 晚间活动建议                             |
| `clothingAdvice`    | 根据可用温度和天气风险生成的穿衣建议     |
| `itemsToPack`       | 随身物品列表                             |
| `warnings`          | 天气风险、数据不足及其他必要注意事项     |

所有必需的字符串字段均应提供有意义的内容。`itemsToPack` 和 `warnings` 应返回列表；无对应内容时返回空列表，不返回 `null`。

本模块不得生成具体景点的营业时间、门票价格、交通路线等未经数据源验证的信息。

## 3. 规则执行总原则

### 3.1 天气优先于普通活动偏好

天气条件优先于用户的一般活动偏好。

当天气条件不适合户外活动时，应优先调整活动安排，并尽可能保留用户偏好的核心目的。

例如：

- 用户选择 `OUTDOOR`，但存在明显降雨风险时，应提供室内替代方案。
- 用户选择 `INDOOR` 时，应以室内活动为主。
- 用户选择 `FOOD` 时，应优先保留美食体验需求；遇到天气风险时，提醒用户注意出行条件。

天气风险不意味着必须完全取消所有户外活动。建议应与风险程度相匹配，不应无依据地使用“禁止出行”等绝对表述。

### 3.2 不编造天气结论

所有天气描述、风险提醒和穿衣建议都必须有可用数据或明确的规则依据。

未知天气代码不得默认归类为晴天；缺失降水概率不得解释为无降雨风险；缺失风速不得解释为无大风。

### 3.3 规则阈值集中管理

温度、降水概率和风速阈值必须集中配置，不得在多个业务方法中重复使用不同的硬编码阈值。

阈值调整后，应同步更新本文件和相关单元测试。

## 4. 天气类型识别规则

天气类型依据 WMO 天气代码分类。实现时应使用明确的代码区间或代码集合，不得仅通过代码大小推测天气类型。

| 天气类型 | WMO 代码       | 业务含义             |
| -------- | -------------- | -------------------- |
| 晴朗     | 0              | 晴朗或晴空           |
| 主要晴朗 | 1              | 主要晴朗             |
| 多云     | 2、3           | 部分多云或阴天       |
| 雾       | 45、48         | 雾或雾凇雾           |
| 毛毛雨   | 51、53、55     | 不同强度的毛毛雨     |
| 冻毛毛雨 | 56、57         | 冻毛毛雨             |
| 降雨     | 61、63、65     | 不同强度的降雨       |
| 冻雨     | 66、67         | 冻雨                 |
| 降雪     | 71、73、75、77 | 降雪或雪粒           |
| 阵雨     | 80、81、82     | 不同强度的阵雨       |
| 阵雪     | 85、86         | 阵雪                 |
| 雷暴     | 95、96、99     | 雷暴及伴随冰雹的雷暴 |
| 未知     | 其他或缺失     | 无法可靠分类         |

实现要求：

1. 对已列出的代码返回对应天气类型。
2. 对未识别代码返回 `UNKNOWN`。
3. 天气代码为 `null` 时，不抛出空指针异常，应标记天气类型未知。
4. 对降雨、冻雨、降雪、阵雨和雷暴等类型，应生成相应天气提醒。
5. 雾天气应提醒用户关注能见度，谨慎安排对能见度敏感的活动。

## 5. 天气风险判断规则

以下阈值是第一版业务实现的建议初始值，正式合并前应由小组确认。它们是本项目的活动建议阈值，不代表官方气象预警标准。

### 5.1 高温

- 判断条件：`maxTemp >= 35°C`。
- 输出：生成高温风险标记。
- 建议：提醒补水、遮阳，避免长时间暴露在高温环境中；优先考虑调整高温时段的户外安排。
- 数据缺失：`maxTemp == null` 时跳过高温判断，并记录该项无法判断。

### 5.2 低温

- 判断条件：`minTemp <= 5°C`。
- 输出：生成低温风险标记。
- 建议：提示穿着保暖衣物，必要时选择室内活动。
- 数据缺失：`minTemp == null` 时跳过低温判断，并记录该项无法判断。

### 5.3 降雨风险

满足以下任一条件时，应考虑生成降雨相关提醒：

1. 天气代码属于毛毛雨、冻毛毛雨、降雨、冻雨或阵雨类别。
2. `precipitationProbability >= 50%`。

建议输出：

- 提醒携带雨伞或雨衣。
- 对户外偏好提供室内替代活动。
- 对已有降雨天气代码的情况，即使降水概率缺失，也应保留基于天气代码的提醒。

降水概率缺失时，不得默认概率为 0%，也不得仅因该字段缺失就认定一定有雨。

### 5.4 降雪、冻雨与雷暴

- 降雪或阵雪：提醒关注路面湿滑、低温及出行条件，酌情调整户外活动。
- 冻雨：提醒注意结冰和滑倒风险，优先建议安全、可行的室内安排。
- 雷暴：优先建议避免在雷暴影响期间进行暴露于室外的活动，并提醒关注当地天气预警。

这些建议属于一般性风险提示，不应将天气代码直接等同于官方预警级别。

### 5.5 大风

- 判断条件：`windSpeed >= 30 km/h`。
- 输出：生成大风风险标记。
- 建议：提醒关注风力，谨慎安排对风力敏感的户外活动。
- 数据缺失：`windSpeed == null` 时跳过大风判断，不得判定为无风。

### 5.6 雾

- 判断条件：天气代码属于雾类别。
- 建议：提醒关注能见度，谨慎安排对能见度有要求的活动。
- 不得在没有额外数据支持的情况下，推断具体能见度数值或交通管制情况。

## 6. 多风险处理与优先级

同一天可能同时出现多种天气风险。所有风险判断应独立执行，不得因为命中一条规则就跳过其他规则。

活动安排采用以下优先级：

1. **严重天气风险：** 雷暴、冻雨等需要特别谨慎对待的天气，优先调整相关户外活动。
2. **明显降水或降雪：** 优先提供室内替代活动，并生成雨雪相关物品建议。
3. **高温、低温、大风或雾：** 根据风险调整活动强度、时段或活动类型。
4. **无明显风险：** 结合用户偏好推荐活动。
5. **数据不足：** 对无法判断的风险明确提示，不得将“未发现风险”解释为“确认安全”。

上述优先级用于决定活动推荐的保守程度，不意味着低优先级风险可以从警告列表中删除。所有已识别风险都应体现在最终建议中。

如果多个风险同时出现，应合并相关建议，避免重复输出相同提醒。

## 7. 活动推荐规则

### 7.1 用户偏好

仅支持以下三种活动偏好：

| 枚举值    | 含义     | 默认推荐方向                       |
| --------- | -------- | ---------------------------------- |
| `OUTDOOR` | 户外游览 | 公园游览、步行、户外休闲等活动类型 |
| `INDOOR`  | 室内休闲 | 室内休闲、阅读、室内参观等活动类型 |
| `FOOD`    | 美食体验 | 餐饮体验、美食探索等活动类型       |

不得将偏好扩展为契约未定义的其他枚举值。

### 7.2 无明显天气风险

- `OUTDOOR`：优先推荐通用户外活动。
- `INDOOR`：优先推荐室内休闲活动。
- `FOOD`：优先推荐美食体验活动。

“无明显天气风险”只表示当前可用数据没有触发本模块已定义的风险规则，不等同于对实际出行安全作出保证。

### 7.3 存在天气风险

- `OUTDOOR`：优先调整为室内替代活动；若仍提供户外活动建议，应同时说明相应风险。
- `INDOOR`：继续推荐室内活动，并附加必要的天气注意事项。
- `FOOD`：保留美食体验偏好，优先建议室内餐饮或其他与天气风险相容的活动类型。

当存在严重天气风险时，安全性优先于用户偏好。

### 7.4 分时段安排

必须生成上午、下午和晚间三个时段的活动建议。

每个时段的建议应：

- 与天气条件和用户偏好一致。
- 不与其他时段的风险提醒相矛盾。
- 在缺乏具体地点数据时，只推荐通用活动类型。
- 不虚构真实景点、营业时间、价格或交通路线。

本版本不要求精确到小时，也不要求获取真实景点信息。

## 8. 穿衣建议生成规则

穿衣建议应优先依据可用的最低温度、最高温度和天气类型生成。

- 最低温度不高于 5°C：建议增加保暖衣物。
- 最高温度不低于 35°C：建议轻便透气衣物，并注意防暑、补水和遮阳。
- 存在降雨、阵雨或降雪：根据天气类型建议相应的防雨或防雪准备。
- 存在大风：在其他天气条件允许的情况下，提醒考虑防风衣物。
- 温度字段缺失：不得生成依赖具体温度的确定性结论；可以根据已知天气类型生成其他有依据的建议。

多个条件同时成立时，应合并建议。例如，高温并伴随降雨时，可以同时提醒选择透气衣物和准备雨具。

## 9. 随身物品生成规则

`itemsToPack` 应根据已识别的天气类型和风险生成。

| 条件               | 建议物品                         |
| ------------------ | -------------------------------- |
| 降雨或较高降水概率 | 雨伞或雨衣                       |
| 高温               | 饮用水、防晒用品                 |
| 低温               | 保暖外套等保暖衣物               |
| 大风               | 视温度情况考虑防风衣物           |
| 降雪或冻雨         | 保暖衣物；必要时提醒关注防滑条件 |
| 雾                 | 根据活动安排提醒关注能见度       |

实现要求：

1. 只添加与天气条件相关的物品。
2. 相同物品不得重复添加。
3. 多种风险同时出现时，应合并所有适用物品。
4. 不得仅因为某字段缺失就添加基于该字段判断的物品。
5. 没有适用物品时返回空列表，而不是 `null`。

## 10. 注意事项生成规则

`warnings` 用于展示天气风险、活动调整建议和数据不足提示。

应至少遵循以下规则：

- 有降雨风险时，说明携带雨具以及可能需要调整户外活动。
- 有高温风险时，说明补水、遮阳和减少高温时段户外暴露的建议。
- 有低温风险时，说明保暖要求。
- 有大风风险时，说明谨慎安排受风力影响的活动。
- 有雷暴、冻雨或降雪等天气时，说明相应风险和保守的活动安排。
- 天气代码未知或关键字段缺失时，明确指出无法判断的内容。

注意事项应简洁、可执行，不应输出无数据依据的风险等级、概率、官方预警或确定性安全承诺。

## 11. 数据缺失与异常处理

### 11.1 部分字段缺失

部分天气字段缺失时，应尽可能利用其他有效字段生成有限建议。

示例：

- 最高温度缺失，但天气代码表明正在降雨：仍可生成雨具建议，但不生成基于最高温度的高温判断。
- 降水概率缺失，但天气代码属于降雨：仍生成降雨提醒。
- 风速缺失，其他天气字段有效：可以继续生成其他建议，但不得宣称不存在大风风险。
- 天气代码未知，但温度有效：可以生成基于温度的建议，同时说明天气类型未知。

### 11.2 严重数据不足

当缺少足以支持计划生成的关键数据时，不得生成看似完整且确定的天气计划。

至少应检查：

- 天气数据对象是否存在。
- 请求日期与天气数据日期是否一致。
- 天气代码、最高温度、最低温度等契约规定的必需字段是否有效。

对于缺少必需字段的情形，应由业务编排层依据团队约定决定返回明确错误，还是生成带有充分限制说明的有限计划。该策略应在实现前统一，并通过测试固定，不能由不同方法自行决定。

请求日期与天气日期不一致时，不得把其他日期的天气直接作为目标日期天气使用。

### 11.3 外部服务异常

天气查询超时、城市无法匹配、日期超出预报范围等情况由天气查询或业务编排层识别并按统一错误约定处理。

业务规则模块不得：

- 将 API 超时当作正常天气。
- 使用当前天气代替目标日期预报。
- 静默吞掉异常并返回伪造的正常计划。

## 12. 计划生成总流程

计划生成模块应按以下逻辑执行：

1. 接收经过校验的 `TravelRequest` 和目标日期对应的 `WeatherData`。
2. 检查天气数据对象及日期一致性。
3. 分析天气代码和可用天气字段。
4. 识别全部可判断的天气风险，并记录无法判断的项目。
5. 结合活动偏好与风险优先级生成上午、下午和晚间活动建议。
6. 生成天气概况、穿衣建议、物品清单和注意事项。
7. 组装 `TravelPlan`，确保必需字段完整、列表不为 `null`。
8. 返回结果供 Controller 和 Thymeleaf 页面使用。

本模块不负责页面 HTML 渲染，也不直接调用外部天气 API。

## 13. 单元测试要求

单元测试应使用构造的 `WeatherData` 和 `TravelRequest`，不依赖真实网络请求。

### 13.1 天气规则测试

至少覆盖：

- 已知 WMO 代码的分类结果。
- 未知天气代码和空天气代码。
- 高温、低温、大风、降雨概率的阈值边界。
- 降雨天气代码与降水概率缺失同时出现的情况。
- 多种天气风险同时成立。
- 可空字段为 `null` 时不发生空指针异常。
- 未知天气不能默认归类为晴天。

### 13.2 活动推荐测试

至少覆盖：

- 三种活动偏好在无明显天气风险时的推荐结果。
- `OUTDOOR` 遇到降雨、雷暴等风险时的替代活动建议。
- `INDOOR` 和 `FOOD` 在风险天气下仍保持合理的偏好方向。
- 多风险同时存在时，严重风险优先影响活动安排。
- 未知天气或数据不足时，不作无依据的确定性推荐。

### 13.3 计划生成测试

至少覆盖：

- `TravelPlan` 所有必需字段均有有效内容。
- `city` 和 `date` 与请求及实际使用的天气数据一致。
- 上午、下午和晚间活动均有建议。
- `itemsToPack` 和 `warnings` 不为 `null`。
- 天气风险与活动、穿衣、物品和注意事项之间保持一致。
- 天气日期不匹配或关键数据严重不足时，按照团队约定处理。
- 更换活动偏好后，重新生成的计划符合新的偏好。

## 14. 验收标准

本模块满足以下条件后，可认为第一版开发完成：

1. 所有规则阈值集中配置，并与本文档一致。
2. 已识别天气类型和风险均能得到相应处理。
3. 三种活动偏好均有可验证的推荐逻辑。
