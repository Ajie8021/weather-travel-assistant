# Agent 业务约束说明

## 1. 文档目的

本文规定天气查询与智能出行 Agent 在天气问答、单日计划生成、连续修改和异常处理中的业务约束。

Agent 负责理解用户意图、判断信息是否充分、选择工具及组织自然语言回复。天气真实性、风险判断和计划生成以服务端天气数据及现有业务服务为准，不得由大模型替代业务规则。

## 2. 规划工具调用规则

### 2.1 需要调用 `generate_travel_plan` 的情况

满足以下条件时，Agent 应调用规划工具：

- 已明确目的地城市。
- 已确定出行日期，或能依据当前日期和用户表述可靠地计算日期。
- 已明确活动偏好，或能够采用系统约定的默认偏好；若项目尚未约定默认值，则应追问。
- 用户要求生成、调整或重新生成单日出行计划。

工具输入必须符合 MCP Schema。日期使用 `YYYY-MM-DD`，活动偏好限定为 `OUTDOOR`、`INDOOR`、`FOOD`。

### 2.2 只查询天气的情况

用户仅询问天气时，应优先调用天气查询工具，不应为了回答天气问题而无条件生成完整行程。

### 2.3 需要追问的情况

以下情况应追问用户，不能自行猜测：

- 城市存在多个合理候选，且无法确定用户所指地点。
- 日期表述不明确，无法可靠换算为具体日期。
- 用户的修改要求缺少必要信息，无法判断需要修改哪个时段或哪项条件。
- 用户提出相互矛盾的约束，且无法同时满足。

追问时应尽量只询问缺失或存在冲突的信息，保留已确认的条件。

## 3. 天气数据与安全规则

### 3.1 天气事实来源

- 具体天气数值必须来自服务端天气查询结果。
- 不得根据语言模型的常识或推测补造温度、降雨概率、风速等数值。
- 不得将未知天气代码直接解释为晴天。
- 天气数据缺失时，应明确说明哪些判断无法完成，不得把缺失值当作零或无风险。

### 3.2 风险阈值

沿用现有 `TravelRuleService` 中集中管理的项目阈值：

- 高温：最高气温大于或等于 35°C。
- 低温：最低气温小于或等于 5°C。
- 大风：风速大于或等于 30 km/h。
- 降雨风险：降水概率大于或等于 50%。

这些阈值是项目业务规则，不等同于官方气象预警标准。修改阈值时，应同步更新规则实现、测试和本文档。

### 3.3 多风险与偏好冲突

- 多种风险同时存在时，应保留所有已识别的风险提示。
- 天气安全要求优先于用户的活动偏好。
- 用户偏好户外活动但天气风险较高时，应调整相关时段的建议，或提供可行的室内替代方案。
- 若关键天气数据不足以支持可靠判断，应明确说明限制，不得输出确定性的天气结论。

## 4. 连续修改规则

### 4.1 保留未修改条件

在同一会话中，用户修改计划时，应继承上一轮仍然有效的条件，包括：

- 目的地城市；
- 出行日期；
- 活动偏好；
- 未被用户要求修改的时段安排及其他约束。

如果用户明确更改某项条件，应以最新、明确的用户要求为准。

### 4.2 局部修改与重新规划

- 用户要求修改某个时段时，应优先调整该时段，同时检查调整是否与天气风险及其他时段安排冲突。
- 城市、日期或活动偏好发生变化时，应基于新条件重新获取所需天气数据并生成计划。
- 不得只修改自然语言解释，却继续返回旧的结构化计划。
- 新计划的城市、日期、活动内容、穿衣建议、携带物品和风险提示必须相互一致。

### 4.3 修改前后的一致性

重新规划完成后，应检查：

1. 新计划的城市和日期与当前有效条件一致。
2. 未修改的条件得到保留。
3. 用户要求修改的时段或偏好在结构化计划中得到体现。
4. 天气风险与活动安排不存在明显矛盾。
5. 自然语言回复准确描述实际发生的修改，不声称完成未执行的操作。

若无法可靠完成修改，应解释原因并请求必要信息，而不是宣称修改成功。

## 5. 不得编造的信息

没有可信数据来源时，不得把以下信息描述为已经核实的事实：

- 具体景点的实时票价；
- 景点的实际营业时间；
- 精确的交通路线、行程耗时或交通时刻；
- 未经查询的天气数值；
- 未经工具执行的查询或规划结果。

可以提供一般性建议，但应明确其属于建议，而非已核实的实时信息。

## 6. 异常处理

| 异常情况             | 业务行为                                   |
| -------------------- | ------------------------------------------ |
| 城市未找到           | 提示用户检查城市名称或提供更具体的地区     |
| 城市存在歧义         | 展示候选或追问，不静默选择首项             |
| 日期超出天气预报范围 | 明确告知当前无法提供该日期的可靠预报       |
| 天气服务超时或不可用 | 提示查询失败，不使用虚构数据生成确定性计划 |
| 部分天气字段缺失     | 使用可用数据，并说明无法判断的部分         |
| 关键数据严重不足     | 拒绝给出缺乏依据的天气结论或计划           |
| MCP 工具调用失败     | 如实报告失败，避免无限重试                 |
| 用户修改要求不明确   | 追问缺失信息，并保留已有有效条件           |

错误码应沿用既有接口契约。新增错误码或修改错误语义时，须经团队评审。

## 7. 职责边界

- `TravelRuleService`：负责天气代码分类、风险判断和规则相关建议。
- `TravelPlanService`：负责根据请求与天气数据生成结构化单日计划。
- `TravelPlanTools`：负责 MCP 参数校验、调用服务及返回规划结果，不重复实现天气规则。
- Agent（由成员 C 集成）：负责意图理解、追问、会话上下文、工具选择和自然语言解释。
- 测试成员：负责独立的需求追踪、集成测试、缺陷记录与验收。

## 8. 验收标准

- MCP Inspector 能发现并调用 `generate_travel_plan`。
- 规则阈值边界、未知天气代码、缺失字段和多风险测试通过。
- 生成的 `TravelPlan` 必需字段完整。
- 连续修改时，未修改条件得到保留，修改后的结构化结果与用户要求一致。
- 自然语言回复与实际工具结果一致，不编造天气、票价、营业时间或精确路线。
- 与成员 C 完成至少三轮连续对话联调，并检查城市、日期、偏好和局部时段修改。
