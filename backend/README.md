# 后端模块协作约定

-   文档版本：1.0
-   适用范围：Java + Spring Boot + Thymeleaf 第一版
-   关联文档：`需求文档.docx`、`travel-assistant.yaml`
-   用途：统一后端模块职责、内部调用、天气规则、缺失数据处理和测试约定。
-   优先级：业务目标以需求规格说明书为准；对外请求参数、公共数据结构、日期语义及页面响应方式以`travel-assistant.yaml`为准；本文补充模块内部协作细节，不替代或擅自修改前述文件。

## 一、公共数据结构

### 1.1 基本原则

公共 DTO 的字段名称、字段含义、枚举值、日期格式及可空语义应与`travel-assistant.yaml`一致。不同模块不得定义含义不同的同名字段。确需修改公共字段时，应先与相关负责人协商，并同步更新契约、实现和测试。

| 数据结构        | 用途与约定                                                   |
| --------------- | ------------------------------------------------------------ |
| `TravelRequest` | 接收目的地、出行日期和活动偏好；必需字段为 `city`、`date`、`activityPreference`。 |
| `WeatherData`   | 保存地理编码及天气 API 结果经解析、标准化后的数据；天气服务负责获取和转换，规则模块不直接解析 Open-Meteo 原始JSON。 |
| `TravelPlan`    | 保存天气概况、上午/下午/晚间活动、穿衣建议、物品清单和注意事项；计划生成模块负责组装，页面模块按契约字段展示。 |
| `ErrorResponse` | 统一描述错误语义，供异常处理、日志和测试使用；当前普通页面流程不要求直接向浏览器输出 JSON。 |

### 1.2 字段语义

1.  `city` 去除首尾空白后不能为空；`date` 使用`YYYY-MM-DD`，表示目的地当地日期；`activityPreference` 只能为`OUTDOOR`、`INDOOR`、`FOOD`。
2.  `WeatherData` 是标准化后的内部模型，不是 Open-Meteo原始响应的直接转发。天气日期必须与用户选择日期一致。温度单位为°C，降水概率为 %，降水量为 mm，风速统一为 km/h。
3.  天气字段允许缺失时使用 `null`。缺失值不得用`0`、晴天、无降雨或无大风替代；未知天气代码不得默认映射为晴天。
4.  `TravelPlan`应返回契约规定的全部必需字段。数据不足时，应在天气概况或相关建议中说明判断限制。`itemsToPack`、`warnings`没有额外项目时可为空数组，但不能遗漏已识别风险。
5.  第一版仅生成单日计划。推荐通用活动类型，不编造真实景点开放时间、票价、交通信息或精确路线。

## 二、模块职责与调用关系

### 2.1 推荐流程

``` text
用户提交表单 / Controller 接收请求
                ↓
请求校验与标准化（TravelRequest）
                ↓
天气服务：地理编码、查询预报、解析原始响应
                ↓
标准化天气数据（WeatherData）
                ↓
天气规则服务：天气分类、风险识别
                ↓
计划生成服务：结合偏好组装单日计划（TravelPlan）
                ↓
Controller 将结果交给 Thymeleaf 页面展示
```

天气 API 请求、业务规则判断和计划生成应职责分离。

规则服务不得直接请求外部天气API；计划生成服务不应重复解析原始天气响应。

Controller主要负责接收请求、调用服务、选择页面和组织提示，不应承载大量天气判断逻辑。

### 2.2 建议的 Java 内部方法

以下是模块之间的**内部调用建议，不是 OpenAPI 契约规定的 Java方法签名**。编码前应检查仓库已有类和方法。若已有等价实现但命名不同，可沿用现有实现，不必为统一名称而重写；跨模块调用的职责、输入输出和异常约定必须统一。

| 模块         | 建议方法形式                                               | 输入                               | 输出与职责                                     |
| ------------ | ---------------------------------------------------------- | ---------------------------------- | ---------------------------------------------- |
| 天气服务     | `getWeather(TravelRequest request)`                        | 城市、日期等请求信息 `WeatherData` | 负责地理编码、天气查询、数据转换和服务异常识别 |
| 天气规则服务 | `analyze(WeatherData weather)`                             | 标准化天气数据                     | 天气分类、风险及数据完整性分析结果             |
| 计划生成服务 | `generatePlan(TravelRequest request, WeatherData weather)` | 用户请求、天气数据 `TravelPlan`    | 结合天气分析和活动偏好生成分时段安排及建议     |

规则服务可以使用内部 `WeatherAnalysis` 对象保存分析结果，但该类不是OpenAPI 公共数据结构；是否新增应结合现有代码决定。

### 2.3 异常处理职责

- **请求校验层 / Controller：**
  校验必填参数、日期格式和活动偏好；非法请求不得进入正常计划生成流程。

- **天气服务：** 

  处理地理编码、外部 API 请求、超时、响应异常和原始数据解析；将可识别失败转换为统一业务异常或错误语义。

- **天气规则服务：**
  显式处理未知天气代码和可空字段，不以默认值掩盖数据缺失。

- **计划生成服务：**
  协调规则分析与计划组装，不得无故吞掉下游异常或生成缺乏依据的天气结论。

- **统一异常处理与页面层：** 

  按契约处理 HTTP状态和页面展示；向用户提供友好提示，不展示堆栈信息。

## 三、天气规则与计划生成标准

### 3.1 阈值与配置

需求文档要求规则阈值集中配置，但未规定以下具体数值。为便于第一版实现和测试，建议先采用下表作为**项目初始阈值**，集中放在配置类或配置文件中，避免散落在多个业务类中。它们是项目业务规则，不是气象部门的官方预警标准；若团队调整，应同步更新测试和本文。

| 判断项目     | 建议初始阈值    | 建议处理方式                                 |
| :----------- | :-------------- | :------------------------------------------- |
| 高温         | 最高气温 ≥ 35°C | 提醒防暑、补水和遮阳；谨慎安排长时间户外活动 |
| 低温         | 最低气温 ≤ 5°C  | 提醒保暖，并结合天气状况调整活动             |
| 大风         | 风速 ≥ 30 km/h  | 提醒关注风力，谨慎安排对风敏感的户外活动     |
| 降雨风险提醒 | 降雨概率 ≥ 50%  | 提醒携带雨具，并评估户外活动是否需要替代方案 |

天气代码表示的降雨、降雪等情况也应参与活动调整，不能只依据降雨概率阈值决定是否提醒。降雨概率缺失时不得视为 0%；可以结合其他有效数据给出有依据的提醒，同时说明无法判断的部分。

### 3.2 天气分类与活动推荐

天气代码按 Open-Meteo 使用的 WMO天气代码进行显式映射，至少区分晴朗、阴天/多云、雾、降雨、降雪及雷暴等情况，并保留未知或未支持代码的处理分支。具体映射应集中定义并由单元测试覆盖；不得通过"未匹配即晴天"处理未知代码。

活动建议结合 `activityPreference` 与天气分析结果：

-   `OUTDOOR`：天气相对适宜时优先推荐通用户外活动；存在可能影响安全或舒适度的天气时，调整活动或给出室内替代建议。
-   `INDOOR`：优先推荐通用室内休闲活动；仍应提供天气相关的穿衣、携带物品和出行提醒。
-   `FOOD`：优先推荐餐饮、美食体验等通用活动类型，并结合天气提供出行建议。

天气条件优先于普通活动偏好。建议以通用活动类型为主，不依赖未接入的数据虚构具体景点、营业时间、价格、交通或路线。

### 3.3 多种风险同时出现

1.  **安全优先：** 明显恶劣天气或可能影响出行安全的情况优先处理。
2.  **风险分别识别：**
    高温、低温、大风、降雨、降雪等风险可以同时存在，应保留所有已识别且有依据的提醒。
3.  **建议保持一致：** 活动安排、穿衣建议、携带物品和 `warnings`
    不应相互矛盾。例如识别到较高降雨风险时，应评估雨具和户外活动调整。
4.  **明确未知状态：**
    对无法判断的风险说明信息不足，不把"未知"写成"没有风险"。

## 四、缺失天气数据与错误处理

### 4.1 缺失数据处理

| 缺失或异常内容     | 处理原则                                                     |
| :----------------- | :----------------------------------------------------------- |
| 天气代码缺失或未知 | 不推断为晴天；无法分类时说明情况                             |
| 最高或最低气温缺失 | 跳过依赖该值的高温或低温判断，不生成确定性温度结论           |
| 降雨概率缺失       | 不推断为 0%；可结合其他有效数据判断，并说明限制              |
| 降水量缺失         | 不推断为无降水；跳过依赖降水量的判断                         |
| 风速缺失           | 不进行基于风速阈值的大风判断                                 |
| 部分字段缺失       | 仍可生成其他数据足以支持的建议，并说明受影响的判断           |
| 关键数据严重不足   | 无法形成有依据的天气概况或计划时，按契约错误语义提示数据不足，不编造天气信息 |

缺失某项数据不等于整个计划必须失败。应尽可能利用有效数据提供有限且有依据的建议；“严重不足”的边界应根据实际字段及计划所需判断决定，并通过测试固定行为。

### 4.2 错误码与责任模块

错误码沿用 `travel-assistant.yaml`，不得另造同义错误码。

| 错误码                        | 含义                                             | 主要识别 / 处理位置                            |
| ----------------------------- | ------------------------------------------------ | ---------------------------------------------- |
| `INVALID_INPUT`               | 必填字段缺失、城市为空、日期无效或活动偏好不合法 | 请求校验层 / Controller                        |
| `CITY_NOT_FOUND`              | 地理编码未找到匹配地点                           | 地理编码 / 天气服务                            |
| `CITY_AMBIGUOUS`              | 存在多个合理地点候选，无法可靠确定目的地         | 地理编码/天气服务 (页面提示用户确认或补充地区) |
| `OUT_OF_FORECAST_RANGE`       | 出行日期超出天气服务实际支持的预报范围           | 天气服务                                       |
| `API_TIMEOUT`                 | 外部天气服务请求超时                             | 天气服务                                       |
| `WEATHER_SERVICE_UNAVAILABLE` | 天气服务错误或暂时不可用（非超时）               | 天气服务                                       |
| `WEATHER_DATA_INCOMPLETE`     | 数据不足以支持所需天气判断                       | 天气解析或规则服务（按实际发现位置处理）       |
| `INTERNAL_ERROR`              | 未预期的内部错误                                 | 统一异常处理机制                               |

错误码描述的是**业务错误语义**，不代表每个错误码都必须对应独立 HTTP
状态码或直接返回 JSON。根据 `travel-assistant.yaml`的页面流程约定：

-   成功或已处理的业务结果通常返回 Thymeleaf HTML页面；城市未找到、城市歧义、超出预报范围、数据不足等情况可通过页面提示呈现。
-   请求格式错误或缺少必填参数使用 HTTP`400`，并按页面流程重新渲染页面显示提示。
-   天气服务不可用使用 HTTP`503`，页面应提示服务暂时不可用，不展示伪造天气数据。
-   普通浏览器页面流程不应在没有约定的情况下随机返回JSON。`ErrorResponse`用于统一错误语义，也可供日志、测试或未来明确约定的 JSON 接口复用。
-   对用户展示友好提示；内部日志可记录诊断信息，但不得把堆栈直接展示给用户。

## 五、测试与联调要求

### 5.1 规则服务与计划生成单元测试

规则服务和计划生成服务的单元测试应优先使用构造的
`WeatherData`，不依赖真实天气 API，以保证可重复性。至少覆盖：

1.  晴朗或相对适宜天气 + `OUTDOOR`：推荐合理的通用户外活动。
2.  有降雨风险 + `OUTDOOR`：给出雨具提醒，并评估室内替代方案或活动调整。
3.  高温、低温、大风分别触发相应提醒；覆盖阈值边界值。
4.  多种风险同时出现：风险不遗漏，活动、穿衣、物品与注意事项保持一致。
5.  未知天气代码及气温、降雨概率、降水量、风速等字段缺失：不作无依据判断。
6.  `INDOOR` 与 `FOOD` 偏好：建议符合偏好，同时遵循天气安全规则。
7.  计划结果包含契约要求的全部字段；无额外物品或提醒时，列表字段使用空数组而非`null`（如团队没有另行确认约定）。

### 5.2 天气服务与整体流程测试

天气服务测试覆盖正常数据转换、城市未找到、城市歧义、日期超出预报范围、请求超时、服务不可用和部分字段缺失。

外部API 测试尽量使用mock/stub，避免单元测试依赖网络；必要的真实接口验证可作为单独的集成检查。

整体流程至少验证：用户修改城市、日期或活动偏好后重新提交，页面结果对应最新请求；输入错误、业务错误及服务异常均能得到符合契约的页面提示。

## 六、实施与变更约定

1.  编码前，各模块负责人应核对仓库中的实际DTO、服务类和方法签名。本文中的方法名是推荐形式，不要求覆盖已有的等价实现。
2.  公共DTO、枚举、错误码、日期语义、天气字段单位或页面响应方式发生变化时，先与相关负责人确认，再同步更新`travel-assistant.yaml`、代码和测试。
3.  修改天气阈值或天气代码映射时，应同步调整边界测试。
4.  第一版不额外引入需求文档未要求的复杂规则引擎、真实景点数据库、精确路线规划或多日计划。
5.  出现本文未覆盖的实现分歧时，以需求规格说明书确定业务目标，以 OpenAPI 契约确定对外字段和页面交互约定，再由相关模块负责人协商内部实现；不得由单个模块私自改变公共约定。
