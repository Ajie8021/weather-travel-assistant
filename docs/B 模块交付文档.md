# B 模块交付文档

## 1. 交付概述

### 1.1 模块名称

天气业务规则与出行计划生成模块（B 模块）。

### 1.2 模块目标

根据用户提供的城市、出行日期和活动偏好，结合可信的天气数据，分析天气风险并生成结构化出行计划，为上层 Agent 提供可调用的业务能力。

本模块主要负责业务规则判断、活动推荐、出行建议生成、规划工具封装及相关单元测试，不负责聊天界面、对话会话管理或天气数据源本身的实现。

### 1.3 交付范围

本次交付包括：

- 天气风险判断及业务规则实现。
- 出行计划生成服务。
- `generate_travel_plan` 规划工具。
- 相关参数校验、异常处理和单元测试。
- 业务规则及模块调用约定等相关文档。

## 2. 模块结构与实现内容

| 模块 / 类                 | 主要职责                                                     |
| ------------------------- | ------------------------------------------------------------ |
| `TravelRuleService`       | 分析天气数据，识别高温、低温、大风、降水等风险，形成规则判断结果。 |
| `TravelPlanService`       | 根据出行请求、天气数据和业务规则，生成完整的出行计划。       |
| `TravelPlanTools`         | 封装 `generate_travel_plan` 工具，校验输入参数、获取天气数据并调用计划生成服务。 |
| `WeatherDataProvider`     | 定义天气数据获取接口，为计划生成模块提供天气数据。           |
| `WeatherDataProviderImpl` | 实现天气数据获取接口，衔接天气数据服务。                     |
| `TravelRequest`           | 封装城市、出行日期和活动偏好等请求信息。                     |
| `TravelPlan`              | 封装天气摘要、分时段活动建议、穿衣建议、携带物品及风险提示等计划结果。 |

上述组件按照职责划分，便于独立测试和后续维护。天气数据获取、业务规则判断和计划生成相互分离，降低模块之间的耦合。

## 3. 核心业务规则

### 3.1 天气风险判断

模块针对以下天气条件进行风险判断：

| 风险类型 | 判断条件               |
| -------- | ---------------------- |
| 高温     | 最高气温大于或等于 35℃ |
| 低温     | 最低气温小于或等于 5℃  |
| 大风     | 风速大于或等于 30 km/h |
| 降水     | 降水概率大于或等于 50% |

当多个风险条件同时满足时，应综合考虑相关风险，而不是只处理其中一种情况。

对于缺失的天气字段、未知的天气代码等情况，不直接将其视为天气良好，应避免据此生成缺乏依据的确定性建议。

### 3.2 出行计划生成

模块根据城市、日期、活动偏好和天气情况，生成以下内容：

1. 天气摘要。
2. 上午活动建议。
3. 下午活动建议。
4. 晚间活动建议。
5. 穿衣建议。
6. 建议携带的物品。
7. 天气风险及其他注意事项。

活动偏好包括：

- `OUTDOOR`：户外活动。
- `INDOOR`：室内活动。
- `FOOD`：美食主题。

活动推荐应结合天气风险和用户偏好。存在不适宜户外活动的天气条件时，应优先考虑安全性，并给出相应的调整建议。

### 3.3 输入校验与数据一致性

模块对必要的请求参数进行校验，并关注以下约束：

- 城市和日期等必要参数应符合接口要求。
- 天气数据对应的城市、日期应与出行请求一致。
- 天气数据缺失或服务调用失败时，不应使用虚构的天气信息补全计划。
- 不应将未知天气状况直接解释为晴好天气。
- 活动建议应符合天气风险和业务规则。

## 4. 对外调用接口

### 4.1 规划工具

工具名称：`generate_travel_plan`

工具通过 MCP 工具注解对外提供调用能力，并启用输出 Schema 生成。

主要输入参数如下：

| 参数                 | 含义     | 说明                          |
| -------------------- | -------- | ----------------------------- |
| `city`               | 目标城市 | 出行目的地                    |
| `date`               | 出行日期 | 日期字符串，按接口约定解析    |
| `activityPreference` | 活动偏好 | `OUTDOOR`、`INDOOR` 或 `FOOD` |

实际工具调用参数名称及序列化格式以代码中的工具定义为准。

### 4.2 调用处理流程

1. 接收并校验工具输入参数。
2. 通过 `WeatherDataProvider` 获取可信天气数据。
3. 将请求参数封装为 `TravelRequest`。
4. 调用 `TravelPlanService.generatePlan(request, weather)`。
5. 由 `TravelRuleService` 执行天气风险判断。
6. 生成结构化 `TravelPlan` 并返回调用结果。

### 4.3 输出数据

`TravelPlan` 包含以下主要字段：

| 字段                | 含义                          |
| ------------------- | ----------------------------- |
| `city`              | 出行城市                      |
| `date`              | 出行日期，格式为 `YYYY-MM-DD` |
| `weatherSummary`    | 天气摘要                      |
| `morningActivity`   | 上午活动建议                  |
| `afternoonActivity` | 下午活动建议                  |
| `eveningActivity`   | 晚间活动建议                  |
| `clothingAdvice`    | 穿衣建议                      |
| `itemsToPack`       | 建议携带的物品                |
| `warnings`          | 风险提示及注意事项            |

以上字段以当前 `TravelPlan` DTO 的实际定义为准。

## 5. 多轮计划修改的协作约定

针对用户在对话中提出的计划修改需求，B 模块负责提供相应的业务规则和计划生成能力，C 模块负责 Agent 的上下文管理、意图识别及工具调用编排。

主要约定如下：

- **修改指定时段：** 例如将下午活动改为室内活动，应保留城市、日期及其他未要求修改的计划字段。
- **修改活动偏好：** 例如将主题改为美食，应根据新的偏好重新生成相关活动建议。
- **修改出行日期：** 应重新获取对应日期的天气数据，再生成计划。
- **修改目的地：** 应使用新的城市重新获取天气数据；目的地不明确时，应先向用户确认。
- **修改后重新校验：** 所有修改后的活动建议仍须符合天气风险和业务规则。

需要说明的是，多轮对话的历史记录、当前计划的保存与恢复，以及修改请求的识别和分发，属于 C 模块的 Agent 编排与会话管理职责。B 模块的业务能力不能替代上述工作。

## 7. 异常处理与限制

模块应针对以下情况进行校验或异常处理：

- 请求参数缺失或格式不正确。
- 天气数据获取失败或数据不完整。
- 天气数据与目标城市、出行日期不一致。
- 活动偏好不合法。
- 天气风险不适合原定活动安排。

异常情况下，应返回与项目接口约定一致的错误结果或异常信息，避免生成依赖虚构天气数据的计划。

此外，活动推荐属于基于天气和业务规则生成的建议。对于实时交通、精确路线、营业时间、价格等未经数据源验证的信息，不能将其作为已确认事实返回。
