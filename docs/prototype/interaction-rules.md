# 慢游指南前台交互说明

负责人：李蔓淇。后台管理由曾盈洁负责。前台使用浅底、深绿主操作和琥珀色风险提示；与后台的视觉规范及入口仍需联调。

## 缩写

API 为应用程序接口，HTML 为超文本标记语言，JSON 为 JavaScript 对象表示法，POI 为兴趣点。

## 演示主线

从首页进入天气查询，保留广州和 2026-11-23，点击查询。点击「用此天气生成行程」，保留户外偏好并提交。降雨冲突弹窗出现后，可先取消查看原行程，再点击「查看冲突与调整」。选择「确认调整下午」，选择室内活动并应用。核对上午和晚间保持原样、下午更新、风险重检结果可见。保存后在历史中查看。示例数据保存在当前页面内存。

## 页面与接口

| 页面 | 操作与请求 | 成功显示 | 失败或空状态 |
|---|---|---|---|
| 首页 | 选择天气、景点、路线或聊天入口 | 打开对应页面 | 页面导航保留在顶部 |
| 天气查询 | 提交 `GET /weather?city=…&date=…`，现有接口服务端渲染 HTML | 城市、日期、`minTemp`、`maxTemp`、`precipitationProbability`、`windSpeed`；计划表单沿用城市和日期 | 空城市、无预报、重名城市及服务异常分别提示；缺失天气字段显示暂无数据 |
| 景点搜索与详情 | 搜索对应成员一设计的 `GET /api/attractions`；详情使用选中搜索结果；收藏需持久化接口 | 景点名称、类别、地址；可收藏或设为路线终点 | 空列表建议换关键词；缺失评分或开放时间显示暂无数据；超时保留输入 |
| 路线比较 | 选择不同起终点，按方式调用成员一设计的 `POST /api/routes/plan` | 步行、公交、驾车的距离与时长 | 同起终点阻止请求；某方式无路线时保留其他结果 |
| 一日游计划 | 当前 `POST /plan/generate` 使用 `city`、`date`、`activityPreference`，返回 HTML；预算与真实景点计划对应待集成的 `POST /api/plans/generate` | 上午、下午、晚间；当前基础计划字段为 `morningActivity`、`afternoonActivity`、`eveningActivity` | 参数错误保留输入；天气不足提示查询失败或风险判断数据不足 |
| 聊天助手 | `POST /api/chat` 提交 `message` 和上轮返回的 `sessionId`；首轮可省略标识 | 展示 `reply`，有值时展示 `weather` 或 `travelPlan`，可展示 `toolCalls` | `NEEDS_INPUT` 继续追问，`FAILED` 给出可重试提示；空消息与超长消息阻止发送 |
| 冲突确认弹窗 | 设计阶段按 `needConfirm=true` 显示风险；取消时保留原行程，确认后打开修改页 | 显示风险原因、目标时段与可选操作 | 风险判断数据不足时显式说明 |
| 局部修改 | 确认后提交目标时段、替换要求与当前计划版本；拟接入 `POST /api/plans/modify` | 应用成功后仅更新下午，再展示重检结果 | 失败、取消或版本冲突时保留原行程 |
| 历史与收藏 | 保存计划、浏览历史和收藏；待定义持久化接口，对应 `travel_plan`、`schedule_item`、`attraction_favorite` | 展示已保存行程及已收藏景点 | 分别提供空历史和空收藏引导 |
| 异常提示 | 所有请求页均有服务异常演示入口 | 返回来源页面保留输入以便重试 | 超时时保留已有结果，不用示例结果顶替真实响应 |

当前仓库的正式字段依据 `openapi/travel-assistant.yaml`。成员一总览列出的景点、路线、真实景点计划与修改入口用于设计对齐，具体请求参数和响应字段需以成员一独立接口稿及最终集成分支复核。原型的广州示例、80% 降水与路线数字用于演示，不定义后端阈值。聊天计划与真实景点计划使用各自的结构。

## 页面状态

请求处理中显示「正在处理…」并禁用当前提交按钮；输入错误在表单附近提示；景点搜索无结果提示更换关键词；服务异常页提供回到来源页重试的操作。日期按目的地当地日期解释。原型期间，用户可从任何请求页进入异常示例来复核保留输入的交互。
